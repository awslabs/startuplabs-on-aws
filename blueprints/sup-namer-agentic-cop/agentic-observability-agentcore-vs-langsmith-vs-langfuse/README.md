# Agentic Observability & Evaluations on AWS — AgentCore, LangSmith & Langfuse

A **LangGraph shopping assistant** running on **Amazon EKS**, calling **Amazon
Bedrock (Claude Sonnet 5)**, and instrumented **simultaneously** for three
observability platforms so you can watch the same agent traffic in all three at
once:

- **AgentCore Observability** — AWS-native (OpenTelemetry → X-Ray + CloudWatch,
  surfaced in the Bedrock AgentCore GenAI Observability console). Auth is the
  pod's IAM role (IRSA) — no keys.
- **LangSmith** — LangChain's SaaS tracing/eval product.
- **Langfuse** — open-source, OTEL-native, SaaS or self-hosted.

The agent exposes seven shopping tools (search, compare, inventory, shipping,
promotions, recommendations, details). It's deliberately ordinary — the point of
the sample is the **instrumentation**, and specifically how little of it is
agent-specific.

The whole stack deploys with one command (`cdk deploy --all`) via a single Python
AWS CDK app and tears down with `cdk destroy --all`.

```
                LangGraph agent  (one /chat request)
                          │
      ┌───────────────────┼────────────────────┐
      ▼                   ▼                     ▼
 OTEL spans          LangChain SDK         Langfuse SDK
 (SigV4 OTLP)         (env only)         (handler + span)
      │                   │                     │
      ▼                   ▼                     ▼
 X-Ray + CWL         LangSmith              Langfuse
      │                (cloud)              (cloud/self)
      ▼
 AgentCore GenAI Observability
 (Sessions · Traces · Evaluations)
```

---

## TL;DR — Which observability platform is right for me?

You don't actually have to pick one — this sample runs all three side by side so
you can compare them on your own traffic. But if you're choosing for a real
project:

- **AgentCore** — best for **AWS-native teams**. Telemetry stays in your account
  (X-Ray + CloudWatch, no data egress), auth is IAM-only (no API keys), and it's
  framework-agnostic because it's built on OpenTelemetry. Consumption-priced;
  broadest compliance (SOC 2, HIPAA, FedRAMP, ISO 27001). Traces in ~5–10 min.
- **LangSmith** — best for **LangChain/LangGraph-first teams** who want the
  fastest, lowest-effort start: tracing is a single env var and the evaluation
  suite is the most mature (30+ built-in evaluators). Managed SaaS (US/EU), free
  up to ~5K traces then per-seat pricing. Traces in ~60s.
- **Langfuse** — best for **multi-framework teams** that need self-hosting / data
  sovereignty or want to stay cost-conscious at scale. Open source (MIT),
  self-host for free or use Cloud (Hobby free → Pro), framework-agnostic via
  SDK/decorator/OTEL. Basic evals (8 evaluators) and a little more integration
  code (see §3). Traces in ~30s.

| | AgentCore | LangSmith | Langfuse |
|---|---|---|---|
| **Best for** | AWS-native, no data egress | LangChain/LangGraph, fastest start | Multi-framework, self-host / cost |
| **Code required** | ~10 lines | ~0 (one env var) | ~20 lines |
| **Auth** | IAM (IRSA), no keys | API key | API key pair |
| **Time to first trace** | ~5–10 min | ~60s | ~30s |
| **Built-in evaluators** | 14 | 30+ | 8 |
| **Hosting** | Your AWS account | Managed SaaS (US/EU) | Self-host or Cloud |
| **Pricing** | Consumption (CW/X-Ray) | Free tier → per-seat | Free (self-host) → per-tier |

## The instrumentation

This is the heart of the sample. Each platform's integration is a clearly
labelled section in [`docker/app/app.py`](docker/app/app.py); the environment
each one needs is generated in
[`stacks/observability_config.py`](stacks/observability_config.py). Here's what
each platform actually costs you in code.

### 1. AgentCore Observability — a few lines + env

Application code (one global instrumentor, plus `session.id` on each request):

```python
# --- init (once) ---
from opentelemetry.instrumentation.langchain import LangchainInstrumentor
LangchainInstrumentor().instrument()   # Traceloop: emits gen_ai.* OTEL spans

# --- per /chat request ---
from opentelemetry import baggage, trace
from opentelemetry.context import attach

ctx = baggage.set_baggage("session.id", request.session_id)
attach(ctx)
span.set_attribute("session.id", request.session_id)

result = agent.invoke(
    initial_state,
    config={"metadata": {"session.id": request.session_id}},  # Traceloop reads this
)
```

Environment (generated by `agentcore_env(cfg)`, injected into the pod — no keys,
SigV4 via IRSA):

```bash
OTEL_PYTHON_DISTRO=aws_distro
OTEL_PYTHON_CONFIGURATOR=aws_configurator
OTEL_EXPORTER_OTLP_PROTOCOL=http/protobuf
OTEL_TRACES_EXPORTER=otlp
OTEL_LOGS_EXPORTER=otlp
OTEL_EXPORTER_OTLP_TRACES_ENDPOINT=https://xray.<region>.amazonaws.com/v1/traces
OTEL_EXPORTER_OTLP_LOGS_ENDPOINT=https://logs.<region>.amazonaws.com/v1/logs
OTEL_EXPORTER_OTLP_LOGS_HEADERS=x-aws-log-group=/aws/bedrock-agentcore/runtimes/<agent>,x-aws-log-stream=runtime-logs,x-aws-metric-namespace=bedrock-agentcore
# These two attributes are what make the GenAI console treat this as an agent:
OTEL_RESOURCE_ATTRIBUTES=service.name=<agent>,aws.log.group.names=/aws/bedrock-agentcore/runtimes/<agent>,cloud.resource_id=<agent>,PlatformType=AWS::BedrockAgentCore,aws.service.type=gen_ai_agent
```

### 2. LangSmith — zero application code (for LangChain/LangGraph agents)

Tracing is fully automatic for LangChain/LangGraph agents once the LangChain SDK sees these env vars
(`langsmith_env(cfg)`):

```bash
LANGCHAIN_TRACING_V2=true
LANGSMITH_PROJECT=<your-project>
LANGCHAIN_ENDPOINT=https://api.smith.langchain.com
LANGCHAIN_API_KEY=<from Kubernetes secret>   # secretKeyRef, never in code
```

> **The "zero code" applies to LangChain-ecosystem agents.** LangGraph isn't the
> classic `AgentExecutor`-style "LangChain agent," but it's built on
> `langchain-core` — its nodes invoke LangChain **Runnables** (e.g.
> `ChatBedrock`), and LangSmith's built-in tracer auto-instruments every Runnable
> when `LANGCHAIN_TRACING_V2=true`. That's the only reason no tracing code is
> needed here. A non-LangChain agent (say a raw `bedrock.converse()` loop or
> another framework) would **not** trace automatically — you'd add the LangSmith
> SDK explicitly (e.g. the `@traceable` decorator or its client wrappers).
> Contrast this with AgentCore above, which is framework-agnostic because it
> consumes OpenTelemetry rather than LangChain callbacks.

### 3. Langfuse — a handler + one span

```python
# --- init (once) ---
from langfuse import get_client, propagate_attributes
from langfuse.langchain import CallbackHandler

langfuse_client = get_client()
langfuse_handler = CallbackHandler() if langfuse_client.auth_check() else None

# --- per /chat request ---
invoke_config = {"metadata": {"session.id": request.session_id},
                 "callbacks": [langfuse_handler]}

with propagate_attributes(session_id=request.session_id, trace_name="chat-request"):
    # a clean (input, output) span for live evaluators to target
    with langfuse_client.start_as_current_observation(
        as_type="span", name="chat-turn", input=request.prompt,
    ) as turn_span:
        result = agent.invoke(initial_state, config=invoke_config)
        turn_span.update(output=response_text)
```

Environment (`langfuse_env(cfg)`):

```bash
LANGFUSE_HOST=https://us.cloud.langfuse.com
LANGFUSE_PUBLIC_KEY=<from Kubernetes secret>   # secretKeyRef
LANGFUSE_SECRET_KEY=<from Kubernetes secret>   # secretKeyRef
```

> **Why the extra code (the manual `chat-turn` span)?** The `CallbackHandler`
> alone captures the LangGraph run tree, but its spans mirror mid-loop framework
> state (e.g. an `AIMessage` full of `tool_calls`) rather than the actual
> question and answer. The explicit `chat-turn` span wraps the turn with a clean
> `(input = user prompt, output = assistant text)` pair so live evaluators have a
> well-formed target to score — LangSmith and AgentCore derive this from their
> own trace models, so they don't need it.

## AgentCore Observability is agent-agnostic

The shopping agent is just a convenient example. **AgentCore Observability and
its evaluations consume OpenTelemetry — not LangGraph.** Any agent, in any
framework or language, appears in the GenAI Observability console and becomes
eligible for AgentCore evaluations as long as it meets these requirements:

1. **Export OTEL spans to the AWS OTLP endpoints** for traces (X-Ray) and logs
   (CloudWatch Logs), authenticated with SigV4 — here that's handled by
   `aws-opentelemetry-distro` using the pod's IRSA role, so there are **no API
   keys**.
2. **Set the two resource attributes** `PlatformType=AWS::BedrockAgentCore` and
   `aws.service.type=gen_ai_agent`. These are the signal that tells the console
   "treat this as an agent," even though it runs on EKS rather than the AgentCore
   managed runtime.
3. **Write to the `/aws/bedrock-agentcore/runtimes/<agent>` log group** and set
   the matching `x-aws-log-group` / `x-aws-log-stream` OTLP headers.
4. **Propagate a `session.id`** so multi-turn conversations group into Sessions.

That's the entire contract. A CrewAI agent, a Strands agent, a bare
`bedrock.converse()` loop, or a non-Python service would light up the same
console with the same four requirements — swap the framework-specific tracer
(here, Traceloop's `LangchainInstrumentor`) for whatever emits OTEL spans in your
stack, and keep the four items above.

**Evaluations build on the same foundation.** Once your agent is emitting the
telemetry above, AgentCore evaluations run **server-side** against the runtime
log group — they read the spans/logs your agent already produces, so any agent
that satisfies the four requirements is evaluable the same way, with no extra
application code. (Contrast the SaaS platforms: LangSmith needs the LangChain SDK
to capture runs, and Langfuse needs the explicit `chat-turn` span above for its
live evaluators to have a clean target.) Setting up evaluators is a follow-up
step to this sample — see [Next step: evaluations](#next-step-evaluations).

## Deploy

Prerequisites: an AWS account + credentials, [AWS CDK v2](https://docs.aws.amazon.com/cdk/v2/guide/getting_started.html),
Python 3.x, and **Bedrock model access** enabled for the model IDs in the target
region. **No local Docker is required** — the agent image is built in AWS
CodeBuild during deploy (the `docker/` folder is uploaded as an S3 asset), so you
don't need Docker Desktop, Finch, Colima, or Podman installed.

```bash
pip install -r requirements.txt
cdk bootstrap          # once per account/region
cdk deploy --all       # ~15+ min (EKS cluster is the long pole)
```

`cdk deploy --all` provisions a dedicated VPC, an EKS 1.30 cluster + node group,
the cluster add-ons (cert-manager, Secrets Store CSI Driver + AWS provider), the
AgentCore log group, CloudWatch Transaction Search, an ECR repo + the CodeBuild
image build, a scoped IAM role + IRSA service account, empty Secrets Manager
secrets, the `SecretProviderClass`, and the agent Deployment + Service. It prints
`ClusterName`, `UpdateKubeconfigCommand`, the secret names, and the
port-forward/test commands as outputs.

> **Tip — kubectl access.** By default only the CDK deploy role is a cluster
> admin, so `kubectl` as your own identity returns *"you must be logged in to the
> server."* Pass `-c clusterAdminRoleArn=<your-iam-role-arn>` on `cdk deploy` to
> have the app grant your principal cluster-admin via an EKS access entry
> automatically.
>
> This must be an **IAM role or user ARN**
> (`arn:aws:iam::<account>:role/<name>`), **not** the output of
> `aws sts get-caller-identity` when you are on an assumed role — that returns an
> STS *session* ARN (`arn:aws:sts::...:assumed-role/...`) which EKS rejects. For
> AWS SSO / IAM Identity Center, use the underlying permission-set role, e.g.
> `arn:aws:iam::<account>:role/aws-reserved/sso.amazonaws.com/AWSReservedSSO_<permission-set>_<hash>`
> (find it with `aws iam list-roles | grep AWSReservedSSO`). The app validates
> this before synth and explains the fix if the ARN is wrong. If you omit the
> flag, grant access after deploy with `aws eks create-access-entry` +
> `aws eks associate-access-policy`.

### Populate the SaaS credentials (LangSmith / Langfuse)

CDK creates the LangSmith and Langfuse secrets **empty** — no credential ever
passes through CDK, CloudFormation, or git. **AgentCore needs nothing here** (it
authenticates with the pod's IAM role via IRSA). LangSmith and Langfuse will
return `401` and produce **no traces** until you complete this section.

> **Read this first — it saves a confusing debugging loop.** The AWS Secrets
> Store CSI Driver creates the in-cluster Kubernetes Secret **once**, the first
> time a pod mounts it, and (with rotation disabled, the default) does **not**
> update it afterward. So if the agent pod starts *before* you populate the
> secrets, it caches the empty values and a plain `kubectl rollout restart`
> will **not** pick up the credentials you add later — you also have to delete
> the stale synced Secret (step 3a below). The cleanest path is to populate the
> credentials **before** the pods come up.

#### 1. Get your keys

- **LangSmith** → Settings → API Keys. The key looks like `lsv2_pt_...`.
- **Langfuse** → Project Settings → API Keys. You get a **public** key
  (`pk-lf-...`) and a **secret** key (`sk-lf-...`).
  - Note your Langfuse **region**: US cloud is `https://us.cloud.langfuse.com`
    (the default), EU cloud is `https://cloud.langfuse.com`. Keys are
    region-scoped — US keys only authenticate against the US host. If your
    project is in the EU (or self-hosted), set the host at deploy time with
    `-c langfuseHost=https://cloud.langfuse.com` (or in `config.json`); the host
    is baked into the Deployment as an env var, so changing it needs a redeploy,
    not just a secret update.
- If you only want to try **one** platform, disable the other at deploy time
  (`-c langsmithEnabled=false` or `-c langfuseEnabled=false`) and skip its
  secret — a disabled platform creates no secret and needs no credential.

#### 2. Store the keys in Secrets Manager

Replace the placeholder values with your real keys (secret names come from the
`LangSmithSecretName` / `LangfuseSecretName` stack outputs; the defaults below
assume the default agent name):

```bash
export AWS_REGION=<your-region>

aws secretsmanager put-secret-value \
  --secret-id "agent-observability/langgraph-shopping-agent/langsmith" \
  --secret-string '{"api-key":"lsv2_pt_XXXX"}'

aws secretsmanager put-secret-value \
  --secret-id "agent-observability/langgraph-shopping-agent/langfuse" \
  --secret-string '{"public-key":"pk-lf-XXXX","secret-key":"sk-lf-XXXX"}'
```

#### 3. Get the credentials into the running pod

**3a. If the agent pod has never started with real keys** (typical first
deploy — you populated the secrets after `cdk deploy`), delete the stale synced
Kubernetes Secret so the CSI driver recreates it from Secrets Manager, then
restart:

```bash
kubectl delete secret langsmith-secret langfuse-secret --ignore-not-found
kubectl rollout restart deployment/langgraph-shopping-agent
kubectl rollout status deployment/langgraph-shopping-agent
```

**3b. If you populated the secrets *before* the pods came up**, no action is
needed — the driver syncs the real values on first mount.

#### 4. Verify the credentials reached the pod

```bash
POD=$(kubectl get pod -l app.kubernetes.io/name=langgraph-shopping-agent \
  -o jsonpath='{.items[0].metadata.name}')

# Env var lengths should all be non-zero:
kubectl exec "$POD" -- sh -c \
  'echo "LANGSMITH=${#LANGCHAIN_API_KEY} LANGFUSE_PUB=${#LANGFUSE_PUBLIC_KEY} LANGFUSE_SEC=${#LANGFUSE_SECRET_KEY}"'

# Startup log should show Langfuse enabled and no LangSmith auth errors:
kubectl logs deployment/langgraph-shopping-agent \
  | grep -iE "Langfuse enabled|Langfuse (auth_check|init) failed|LangSmithAuthError"
```

Expected: non-zero lengths, `✓ Langfuse enabled - traces will be sent to ...`,
and **no** `LangSmithAuthError` / `401`. If you still see `401`:

- **`LangSmithAuthError: 401`** → wrong or truncated LangSmith key (must start
  with `lsv2_pt_`, no trailing spaces). Re-run step 2, then step 3a.
- **Langfuse `401 "Invalid authorization header. Confirm that you've configured
  the correct host."`** → the keys don't match `LANGFUSE_HOST`. Confirm your
  project's region (US vs EU) and either use the matching keys or redeploy with
  the correct `-c langfuseHost=...` (see step 1).

### Test

**1. Point kubectl at the cluster and confirm the pod is running:**

```bash
aws eks update-kubeconfig --name <ClusterName-output> --region <region>
kubectl get pods            # the langgraph-shopping-agent pod should be Running / 1/1
```

**2. Port-forward the Service** (leave this running in its own terminal):

```bash
kubectl port-forward svc/langgraph-shopping-agent 8000:80
```

**3. In another terminal, send a few requests:**

```bash
# Health check — expect: {"status":"healthy"}
curl http://localhost:8000/health

# A shopping prompt
curl -X POST http://localhost:8000/chat \
  -H 'Content-Type: application/json' \
  -d '{"prompt":"Show me laptops","session_id":"test-001"}'

# A follow-up in the SAME session (exercises conversation memory)
curl -X POST http://localhost:8000/chat \
  -H 'Content-Type: application/json' \
  -d '{"prompt":"Which of those is cheapest?","session_id":"test-001"}'
```

Each `/chat` call returns a JSON body with the agent's reply. Then check the
telemetry: traces appear in LangSmith/Langfuse within ~30–60s (only if you
populated their secrets above); the AgentCore GenAI Observability console takes
~5–10 min (X-Ray indexing + Application Signals).

> **Troubleshooting.**
> - **No LangSmith/Langfuse traces, or `401` in the logs** → the credentials
>   didn't reach the pod. See
>   [Populate the SaaS credentials](#populate-the-saas-credentials-langsmith--langfuse)
>   — most often you populated the secrets after first deploy and need the
>   delete-synced-Secret + restart step (3a).
> - **Pod stuck in `CreateContainerConfigError`** → the synced Kubernetes Secret
>   doesn't exist yet; confirm the CSI driver/ASCP add-ons are healthy
>   (`kubectl get pods -n kube-system | grep secrets-store`) and re-run the
>   credentials steps.
> - **A `/chat` call returns `500`** → check the app logs with
>   `kubectl logs deployment/langgraph-shopping-agent`.

## Next Step: Agentic Evaluations

This sample gets you **observability** — traces, sessions, and spans flowing to
all three platforms. **Evaluations are the natural follow-up**, and they build
directly on the telemetry you now have rather than requiring changes to the
agent. Because AgentCore evaluations run server-side against the runtime log
group your agent already writes to, you can add LLM-as-a-judge scoring (built-in
or custom evaluators) without touching application code.

Set them up by following the AWS documentation:
**[Configure evaluators in Amazon Bedrock AgentCore](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/evaluators.html)**.

## Destroy

```bash
cdk destroy --all
```

Two things are intentionally **retained**: the Secrets Manager secrets (`RETAIN`
policy, 7–30 day recovery window — remove with
`aws secretsmanager delete-secret --secret-id <name> --force-delete-without-recovery`)
and the account-level CloudWatch Transaction Search setting (left enabled so it
doesn't disrupt other workloads).
